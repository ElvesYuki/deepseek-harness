# Personal DSH Launcher

[English](README.md) | 中文

## 概述

在 Electron 窗口中运行 DeepSeek Harness，使用独立数据目录、分范围代理、服务控制，以及来自官方 GitHub 仓库的原地更新。此独立项目不加入 DSH 的 pnpm workspace。构建目标包括 macOS Apple Silicon 和 Windows x64，不替代官方 Desktop 应用。Windows 安装包必须在 Windows 上完成构建并通过冒烟检查，才能视为可交付。

## 构建与运行 {#build-and-run}

开发者需要 Git、Node.js、npm 以及 DSH 所需的原生构建工具。在 `desktop-launcher/` 中执行：

```sh
npm ci
npm run setup:electron
npm run prepare:payload
npm start
```

启动器 `.npmrc` 禁用依赖安装脚本；本地开发或 macOS 打包前，通过 `npm run setup:electron` 显式准备 Electron 可执行文件。Windows 脚本和 CI 显式执行这一步。导出的构建包包含 `.npmrc`，续跑指纹也包含它。DSH 源码安装使用自身的 pnpm 生命周期策略，其子进程环境会移除继承的 npm 配置。

运行包准备会下载并校验 Node.js、desktop/dugite-native 的便携 Git 和 pnpm。它导出当前已提交的 Git 代码，排除此启动器，按锁文件安装 DSH 依赖、构建产品并检查 CLI 入口。准备前必须提交已跟踪文件的修改。未跟踪文件、凭据和本地 `.env` 文件不会复制。构建日志和下载缓存在 `.cache/` 下；准备中断后保留诊断文件，也可能留下锁文件，只有确认准备进程已退出后才能删除锁。

准备运行包后构建本地安装包：

```sh
npm run package:mac
```

DMG 输出在 `.cache/dist/` 下。本地构建没有 Developer ID 签名或 Apple 公证，macOS 可能要求明确的安全授权。缺少运行包时，打包会停止。安装包包含 Git、Node、pnpm、DSH 源码及构建依赖，因此安装时无需安装开发工具或下载 npm 包。模型请求及可选插件下载仍需要网络。

在 macOS 上安装时，挂载 DMG 并双击 `Install DSH Launcher.command`。它把应用安装到 `~/Applications`，准备固定运行目录后才报告完成。如果完全相同的应用已拖入 `/Applications`，则使用该副本；已有不同版本时，需先关闭并替换应用。请保持终端开启直到完成。仅拖拽应用不会准备运行目录：拖拽后仍需运行此命令，或在管理页面明确选择“恢复内置版本”。未签名应用仍可能需要系统安全授权；该命令不会绕过 Gatekeeper。

Windows Setup 在完成页面之前调用相同的 `--install-runtime` 模式，非零退出码会使安装失败。它以安装用户身份运行，不提权。安装前请关闭启动器；已有实例时安装会失败，不会静默跳过准备。安装不会启动 DSH、下载更新、替换已有运行版本或清除中断的维护记录。部署失败时保留日志并重试安装；未完成的维护需在管理页面使用“修复”或“恢复”。原生 NSIS 执行仍需在 Windows 上验证。

### 从 Windows Git 工作区构建 {#windows-checkout}

可以在 Windows 克隆自己的 fork，再让本地编程 AI 构建启动器。这条路径需要 Git、受支持的 Node.js 与 npm，以及 Windows x64 构建环境；构建包脚本随后会准备自己固定版本的工具。使用较短的本地检出路径，拉取更新前保留已有修改。为源码工作流安装 Git 和 Node 不会改变安装包自带运行工具的要求。

Git 仓库不是解压后的构建包。不要直接运行 `windows/Build-Windows.cmd`。在干净的已提交工作区中进入 `desktop-launcher/`，执行：

```sh
npm ci
npm run export:windows
```

导出器使用 Node 归档库，不依赖 macOS 工具路径或创建符号链接的权限。输出 `WINDOWS_BUILD_DIRECTORY` 指向独立构建目录，在该目录运行 `Build-Windows.cmd`。需要 ZIP 时执行 `npm run export:windows:zip`。快照记录源码提交、版本和 SHA-256；内部链接转为普通副本，越界和循环链接会被拒绝。导出仅包含已提交的源码，排除启动器；不要将凭据或用户数据提交到源码仓库。原生 Windows 验证由 CI 和构建包脚本执行。

在 Windows 工作区中，可以将下面的任务说明交给 AI：

> 阅读仓库 AGENTS.md 和 desktop-launcher/README.zh.md。构建 desktop-launcher 目录下的独立启动器，不是官方 apps/desktop 客户端。 更新前检查 git status 和 fork 远程地址，保留本地修改。 在 desktop-launcher 中运行 npm ci 和 npm run export:windows，生成构建包。 使用选定的已提交源码版本，保留快照哈希及内部链接校验。 不要将凭据或本地用户数据打入快照。 在生成的构建包中运行 Build-Windows.cmd；必要时将我的实际 HTTP 代理 填入 proxy.txt，不修改全局 npm/Git 配置，不关闭 TLS 校验。 保留锁定的依赖版本。若修改启动器版本，只更新 package.json 的 version 以及 package-lock.json 顶层和 packages[""] 中的 version。 不得在依赖记录中全局替换版本字符串。 使用现有构建脚本显式安装 Electron；pnpm 命令必须在声明使用 pnpm 的解压后 DSH 源码目录中执行。 运行包完成后若打包失败，在同一构建包运行 Continue-Packaging.cmd， 复用已下载内容和编译完成的运行包。 不得跳过失败测试；检查 not ok 段落和首个构建错误。 只有单元测试、服务启动重启、打包、端口占用和导入检查全部通过后， 才交付 Setup.exe 路径、SHA-256、源码提交号及 BUILD-SUCCESS.txt。 单独说明尚未验证的安装程序交互。未经我要求，不安装或发布产物。

产物是生成的构建包中 `desktop-launcher/.cache/dist/` 下的未签名 `DSH-Launcher-<version>-Windows-x64-Setup.exe`。构建包根目录的 `BUILD-SUCCESS.txt` 是脚本完成记录；仅在第 7 步前出现可执行文件并不代表完成。重试时沿用同一构建目录，以保留 `proxy.txt`、下载缓存和已完成的运行包。Git 更新只改变源码，不会重建已有安装包或刷新旧的导出构建包。

### Windows 构建包

运行包构建完成并进入打包阶段后，可用 `Continue-Packaging.cmd` 复用现有依赖和运行包，显式安装 Electron，重新执行单元测试、服务和成品检查，而不重新构建 DSH。续跑要求已完成的构建记录与源码压缩包、清单、工具版本和启动器构建及运行代码匹配。记录缺失或输入变化时，须运行 Build-Windows.cmd，下载缓存仍会保留。没有该记录的旧运行包需要完整构建一次。完整构建同样会在测试前显式安装 Electron。

Windows 构建包包含经过校验的当前已提交 DSH 源码快照、本启动器和 `Build-Windows.cmd`。在 Intel/AMD Windows 10/11 电脑上解压到本地短路径后，双击该命令文件。pnpm 版本检查和构建命令均在声明使用 pnpm 的解压后 DSH 源码目录中运行。依赖安装显式使用 npm 官方源，不修改全局 npm 配置。脚本下载固定版本的 Node、Git 和声明的 pnpm，安装依赖、构建 DSH、运行生命周期测试及服务冒烟测试、生成未签名 NSIS 安装包，再验证打包应用的端口占用切换及测试数据导入。所有检查通过后才写入 `BUILD-SUCCESS.txt`；安装包位于 `desktop-launcher/.cache/dist/`。脚本不会安装该产物，也不修改全局 PATH。首次构建需要联网；若原生依赖没有预编译文件，可能需要 C++ 构建工具。命令文件旁可选的 `proxy.txt` 只为本次构建设定 HTTP/HTTPS 代理；空文件或仅含空白的文件不会改变环境中的代理设置。失败时保留 `build-windows.log` 和 `.cache/` 下各步骤日志。只有确认全部构建进程退出后，才能删除残留的 `prepare-windows.lock`。

Windows 包目录链接保存为相对位置元数据，安装部署到最终目录后再创建 junction，避免安装后的运行时引用构建电脑路径。Windows 服务关闭使用 `taskkill /T /F` 并等待所持有的子进程退出。Windows 用户数据位于 `%APPDATA%` 下，默认数据检测使用 `%USERPROFILE%/.dsh`。NSIS 按用户安装，卸载时保留用户数据。macOS 测试不能证明 Windows 构建或原生安装界面已经通过验证。

载荷文件数不匹配时，启动器会阻止首次激活和服务启动。此前已记录为不完整的版本也不能普通启动，必须先修复或恢复。首次准备失败的目录保留在暂存区，直到下次初始化启动器时清理。请重新安装完整安装包；如果此前记录的不完整版本仍阻止启动，请保留日志并使用“修复当前版本”或“恢复内置版本”，不要删除用户数据。文件数校验用于发现条目缺失，不能检测内容损坏。Windows 安装包校验只选择当前启动器版本的 x64 文件名或显式指定的路径；文件不存在时失败，不会改为检查旧安装包。

## 使用启动器 {#use-the-launcher}

标题旁显示从 Electron 读取的启动器版本，与当前 DSH 内核版本分开显示。紧凑管理窗口在顶部保留服务状态和可用操作，下方通过连接设置、官方更新、数据管理和运行日志四个标签切换。深蓝界面使用绿色突出主要操作和运行状态，保留原生窗口控件。连接设置将代理范围分组，默认窗口尺寸下可直接看到保存操作，代理及 API Key 说明默认折叠。服务运行或操作进行时禁用端口输入。标签支持方向键切换，并保留未保存的设置。修改后会显示提示，可撤销修改；保存或撤销前不能测试 GitHub 连接，确保测试使用已保存的配置。

管理窗口在另一个隔离的 Electron 窗口中打开 DSH 工作区。关闭工作区会回到管理窗口，不停止服务。退出启动器时，如果有服务或构建运行，会先请求确认，再停止其拥有的进程树，不终止其他 DSH 应用。

数据目录使用 Electron 的 userData，通常为 `~/Library/Application Support/personal-dsh-launcher`。点击“打开数据目录”确认实际位置。`dsh-home/` 保存独立会话、设置及凭据，`workspace/` 是初始工作目录，`versions/` 保存托管的应用副本，`runtime.json` 记录固定运行目录和中断的维护操作。日志约每 2 MB 轮转一次，并遮盖 URL 查询参数及常见凭据赋值；第三方插件的任意输出仍可能包含敏感信息。

“导入默认数据”自动检测 `~/.dsh`，“重新检测”可刷新结果；“选择目录导入”可选择包含 `sessions/`、`storages/` 或 `profiles/` 的其他 DSH 数据目录。请先停止使用来源目录的所有外部 DSH 进程，并只导入可信数据，因为导入包含配置及凭据。确认后，启动器停止自己的服务，将来源复制到暂存目录，把原数据保留在 `backups/import-…/dsh-home`，再整体替换客户端数据；不合并数据库，也不修改来源。导入后服务保持停止，需手动点击“启动服务”。启动器代理设置和外部项目文件不在导入范围。生成的共享依赖目录 `profiles/node_modules/` 会在检查链接前跳过，包括指向旧安装位置的失效链接。Profile 配置、插件清单及各 profile 自己的依赖仍按正常规则复制；导入操作不会重新安装额外插件。目录重叠以及其他位置的链接或特殊文件会被拒绝，错误提示显示对应的相对路径。替换失败或中断时，会在启动前恢复原数据；恢复失败则阻止启动。复制失败的暂存文件保留供排查。导入不会转换不兼容的会话格式；若启动报告版本错误，请保留备份。

模型 API Key 请在工作区的模型设置中配置，或导入可信的现有 DSH 数据。服务不继承终端中的 API Key。

代理设置接受不含账号密码的 HTTP 或 HTTPS 地址。开关分别控制更新与依赖安装、DSH 服务请求及工作区浏览器流量。本地回环流量绕过代理。服务设置在重启后生效，修改首选端口前必须停止服务。首选端口被占用时，由系统为本次服务分配空闲端口，管理窗口显示实际端口，工作区自动连接新地址。首选设置不变，下次启动仍优先尝试它。连接测试使用已保存的更新代理访问 GitHub，不测试模型提供方。不修改系统代理、Shell 配置或全局 Git 配置。

## 更新与恢复 {#updates-and-recovery}

更新渠道默认为“正式发布版”：选择官方最近发布且不属于预发布的 DSH 版本。“包含预发布版”允许预发布版本；“主分支最新版”固定到“检查更新”时显示的官方 master 提交。更改渠道只影响查询，不修改已安装程序。没有正式版时明确提示，不回退到预发布版。发布查询支持分页。确认提示说明：切换渠道或离线恢复可能选择更旧的程序，其数据读取能力可能与现有数据不兼容。

“更新并启动”先停止服务，再通过深度为一的 fetch 获取选定 tag 或 commit，在同一个运行目录更新，不获取其他标签。多次更新复用 Git 对象库。源码重置及清理会丢弃程序目录内的修改和生成文件；随后按锁文件安装依赖并重新构建。用户会话、配置和凭据位于独立 DSH home 中。更新不创建程序或数据备份。Node 和 pnpm 要求必须与内置工具匹配。构建及 CLI 检查通过后才启动服务；只有服务就绪且成功状态保存后，才清除维护标记。

“修复当前版本”获取并重建当前精确 commit。如果当前提交与内置快照一致，则改用精确匹配的离线载荷恢复，包括官方仓库无法获取的 fork 快照。如果维护中断，“修复”和“重试维护操作”使用已记录的目标。维护失败或中断会阻止普通启动，重开客户端也不能绕过。“恢复内置版本”使用离线载荷，在同一路径重建程序文件，不运行 Git 或下载依赖。恢复来源是当前安装的启动器自带版本，不一定是最早安装的版本。不恢复、降级或删除用户数据：新程序可能已迁移数据。如果旧程序无法读取，请使用兼容的新程序，不要删除数据。

新安装会在 versions/current 中准备独立可写运行目录；已有安装继续使用原 active 目录，因此运行路径不变。文件系统支持时请求写时复制，否则使用普通复制；新运行文件不与恢复载荷建立硬链接。更新旧运行目录前会解除共享硬链接。安装阶段写入运行目录；正式安装的客户端普通启动时不会复制文件，未安装时会明确提示。开发模式及手动恢复可按需准备。原始载荷单独保留在应用内用于离线恢复。这是将工作移到安装阶段，并未消除文件读写；安装时间和磁盘占用仍取决于载荷体积与文件数量。单文件程序分发尚未实现。

从分阶段更新方案升级时，先前准备的版本和历史备份保留在磁盘，但不再通过切换操作选用。已有恢复标记继续阻止普通启动；修复或恢复只在当前路径重建程序，不恢复历史数据。数据导入是独立操作，保持原有备份行为。Git 维护不会修改开发者工作区或启动器自身的应用文件。

## 开发与检查 {#development-and-checks}

```sh
npm run check
npm run test:ui
npm run test:import
npm run test:runtime
npm run test:desktop
npm run test:occupied
npm run test:update
```

独立 lint 和单元检查统一使用 `npm run check`。desktop-launcher 可复用工作流在 Windows 和 macOS 上运行检查、导入冒烟、构建包导出，以及当前源码的真实构建、启动和重启检查。PR CI 调用它并将结果纳入 `all checks passed`；每次 master 推送也会触发，包括仅修改上游代码的提交。手动选择 Windows 安装包选项可运行完整构建。`npm run test:source` 要求先安装根目录依赖并执行 `pnpm run build`，随后用隔离数据和系统分配的端口验证真实 CLI 就绪输出、认证后页面访问和重启；不调用模型，失败时在 `.cache/test-results/source-*/` 保留脱敏日志。工具版本和校验值集中在 `toolchain.json`，pnpm 版本跟随源码清单。`node scripts/size-report.mjs` 统计现有运行包体积，不删除依赖。

导入冒烟测试通过管理按钮和 IPC 使用测试目录及自动确认的测试对话框，检查导入文件及原数据备份，并捕获管理窗口。原生目录选择器本身需手动验证。测试以 TAP 格式在各用例结束时输出失败详情。进程测试从标准输出读取完整的带标记 PID 消息，不将错误输出中的诊断信息作为 PID。服务测试先等待进程退出，再删除临时运行目录。Node 测试覆盖导入替换、复制拒绝、提交失败、中断恢复、设置校验、发布版本输入、进程取消、后代进程清理和中断后的更新恢复。Electron 冒烟测试使用独立测试数据目录打开真实管理窗口，检查渲染文本，并输出 `.cache/test-results/management.png`。它不调用模型，也不代表完整 DSH 兼容性验证。运行包冒烟测试在 PATH 中排除开发工具后，先单独测量安装，再执行两次真实服务启动、HTTP 页面访问及停止，然后在同一路径离线恢复并验证用户数据标记。桌面冒烟测试在 Electron 中打开真实 DSH 页面并输出 `.cache/test-results/workspace.png`。更新冒烟测试使用 LAUNCHER_TEST_TAG 指定的官方 tag，在相同目录重新构建，并检查用户数据标记；它使用专用测试目录，需要更多时间和磁盘空间。运行包准备和打包是独立检查，管理窗口冒烟测试不代表离线安装或真实版本升级已验证。

## 限制 {#limitations}

管理界面为中文。不提供 Intel Mac 打包、代理认证、启动器自身自动更新、磁盘容量预估和自动备份保留策略。工作区渲染器拒绝权限请求，因此麦克风输入及其他需要浏览器授权的功能不可用。首个运行包包含开发依赖以支持现有 DSH 源码启动器，安装包较大。未来源码构建可能需要额外原生编译器或新的内置工具版本。构建运行包可能执行受信任上游的生命周期脚本。发布版本查询依赖 GitHub 连接与限流状态。启动和重启最多等待两分钟，直到 CLI 输出已认证的就绪地址；第三方改变该输出时需要适配启动器。
